## 1. What we are building

`glim` — a keyboard-driven terminal file explorer. Two panes: a navigable directory listing on the
left, a preview of the highlighted entry on the right. Think `ranger` / `lf` / `nnn`, rebuilt as a
React component tree.

## 2. Why *this* project

Every stack has a canonical demo that stresses its actual primitives rather than its marketing:

| Stack | Canonical demo | What it actually proves |
|---|---|---|
| MERN | Todo app | CRUD, routing, persistence, auth boundary |
| three.js | Solar system | scene graph, camera, transforms, animation loop |
| 2D game engine | Brick shooter | game loop, collision, input, sprite state |
| **TUI framework** | **File explorer** | **layout, keyboard state machine, async I/O, viewport windowing, render throughput** |

A todo app in a TUI proves nothing — it is a static list. A file explorer forces every hard problem
the framework has:

- **Layout** — flexbox in a fixed character grid that resizes under you.
- **Keyboard as the only input device** — no mouse, no focus ring, no browser defaults. You own the
  entire input state machine.
- **Real async I/O** — the filesystem is slow, fallible, and permission-gated. `readdir` on a network
  mount takes 900ms and sometimes throws `EACCES`.
- **Viewport windowing** — a directory with 40,000 entries must not render 40,000 rows. There is no
  DOM to virtualize for you.
- **Render throughput** — Ink re-renders by diffing and rewriting terminal lines. Careless state
  updates produce visible flicker. You feel your own mistakes immediately.
- **Graceful degradation** — no TTY, no color, 60-column terminal, no Unicode font.

That is the full surface area of TUI development. Nothing is faked.

## 3. Why Ink (and not the alternatives)

The rest of the TUI world lives outside Node:

| Framework | Language | Verdict |
|---|---|---|
| `ratatui` | Rust | Excellent, immediate-mode, wrong language for this project |
| `Bubble Tea` | Go | Excellent, Elm architecture, wrong language |
| `textual` | Python | Excellent, CSS-like styling, wrong language |
| `blessed` | Node | Imperative, effectively unmaintained, no component model |
| **`ink`** | **Node / TS** | **Chosen** |

Ink is chosen because:

1. **It is React.** Same component model, same hooks, same mental model as the rest of a TypeScript
   developer's day. `useState`, `useEffect`, `useMemo`, custom hooks — all of it transfers.
2. **Yoga flexbox.** `<Box flexDirection="row" flexGrow={1}>` in a terminal. Layout is declarative,
   not manual cursor arithmetic.
3. **First-class testing.** `ink-testing-library` renders to a string. This matters enormously for an
   agent-built project — see §6.
4. **It is what the ecosystem actually ships.** `gatsby`, `prisma`, `shopify` CLI, `cloudflare
   wrangler` and many others render their interactive output through Ink. This is not a toy.
5. **The React knowledge is the trap and the lesson.** Ink punishes React habits that are free in a
   browser — unmemoized children, state updates in a tight loop, rendering long lists. Learning
   *where* React breaks down is half the value of the exercise.

**Non-goal:** we are not building the fastest file manager. We are building the one that best
demonstrates how to write a real Ink application.

## 5. The three stages

Stages are **capability gates**, not sprints. Stage N+1 does not begin until Stage N's Definition of
Done passes in full.

```
        STAGE 1                  STAGE 2                    STAGE 3
      Walking Skeleton         Real Application            Production
  ┌────────────────────┐   ┌────────────────────┐   ┌────────────────────┐
  │ one pane           │   │ two panes + preview│   │ core/ ⟂ ui/ split  │
  │ ↑↓ ⏎ ← q           │   │ filter, sort, hide │   │ memfs + pty tests  │
  │ readdir → list     │   │ colors, theming    │   │ EACCES, symlinks   │
  │ 1 render test      │   │ windowed scroll    │   │ AbortController    │
  │ green pipeline     │   │ loading + errors   │   │ config file        │
  │                    │   │ status bar         │   │ NO_COLOR, no-TTY   │
  │                    │   │                    │   │ CI + npm publish   │
  └────────────────────┘   └────────────────────┘   └────────────────────┘
   "boring and correct"     "good and complete"      "unbreakable and shipped"
```

### The floor (applies from commit #1, not Stage 3)

These are **not** Stage 3 items. Deferring them is what makes Stage 3 a rewrite.

- `tsconfig`: `strict: true`, `noUncheckedIndexedAccess: true`, `verbatimModuleSyntax: true`
- Zero `any`. Lint-level error. `unknown` + narrowing instead.
- Every stage ends with `typecheck && lint && test && build` all green.
- At least one test exists from Stage 1 onward. It never goes to zero.
- No dead code, no commented-out code, no `TODO` without a task ID.
- Conventional commits, one logical change per commit.

What Stage 3 *actually* adds is hardening — adversarial inputs, failure modes, performance proof,
degradation paths, release engineering. Not "the quality pass."

## 6. Verification — the part that decides whether this works

**An agent cannot see a terminal UI.** It will render nothing, assert nothing, and report "the
two-pane layout looks clean and the colors are balanced." This is the single highest-probability
failure mode of this project.

Every claim about the UI must be backed by one of four evidence levels:

| Level | Mechanism | Proves | Available from |
|---|---|---|---|
| **L1 — Frame assertion** | `ink-testing-library` → `lastFrame()` contains/matches | Content is rendered | Stage 1 |
| **L2 — Golden frame** | Snapshot the full `lastFrame()` string to a committed file | Layout is stable and diffable | Stage 2 |
| **L3 — Real TTY** | `node-pty` spawns the built binary, writes keys, reads screen buffer | It works as an actual program | Stage 3 |
| **L4 — Human gate** | A human runs it and confirms | Aesthetics, feel, font rendering | Every stage, explicitly |

**L4 is a hard stop.** Where a stage's DoD contains a `HUMAN GATE`, the agent must halt, state what
it needs looked at, and wait. It may not self-certify and continue.

A golden-frame snapshot is a plain text file. It is reviewable in a diff. Use it.

## 7. Agent mentality per stage

Each stage wants a *different personality*. An agent optimising for Stage 3 values during Stage 1
will over-abstract an app that does not exist yet. An agent carrying Stage 1 values into Stage 3 will
ship something that crashes on a symlink.

### Stage 1 — **The Bricklayer**

> *"Boring, correct, and finished. Cleverness is a liability."*

- Build the dumbest thing that completes the loop: read a directory → show it → move the cursor →
  enter a directory → quit cleanly.
- **Resist abstraction.** No plugin system. No theme engine. No `IFileSystemProvider`. One component
  file is fine. Premature interfaces here become Stage 3 demolition work.
- Duplication is acceptable. Wrong abstractions are not.
- Hardcode what you don't yet understand. Leave it visible, not hidden behind a config.
- Success is `npx glim` opening in the current directory and quitting on `q` without leaving the
  terminal in a broken state.
- **Failure mode to watch for:** building Stage 2 features because they seem easy. They are not in
  scope. Read the OUT-OF-SCOPE list and obey it.

### Stage 2 — **The Craftsperson**

> *"Now make it something a person would actually choose to use."*

- Features and polish, built *inside* the skeleton Stage 1 proved.
- Refactoring is permitted **to enable a feature**, not to satisfy taste. "This would read nicer as a
  reducer" is not a reason. "Filter + sort + selection can no longer be three `useState`s without
  desyncing" is.
- Every visual decision gets a golden-frame snapshot. If it can't be snapshotted, it can't be claimed.
- Performance enters here, but only as a correctness concern: rendering 40,000 rows is a bug, not a
  slow feature. Windowing is a Stage 2 requirement.
- **Failure mode to watch for:** feature sprawl. Bookmarks, tabs, file operations, image previews,
  git status — all tempting, all out of scope. The list is fixed in `v2_STAGE_2.md`.

### Stage 3 — **The Auditor**

> *"Assume it is broken. Prove otherwise. Add no features."*

- Adversarial toward the existing code, including its own earlier work. Hunt for what breaks it.
- Concrete adversaries to defeat, not vague "robustness":
  `EACCES` · `ENOENT` mid-navigation · circular symlink · 40,000-entry directory · 4-byte terminal
  width · `SIGINT` during an async read · rapid key-mash producing out-of-order `readdir` resolution ·
  binary file preview · file with no read permission · `NO_COLOR=1` · piped stdout (no TTY).
- Separates `core/` (pure, no React, fully unit-testable) from `ui/` (Ink components). This is the
  one large refactor the project sanctions, and it happens *here* — after the shape is known.
- **Adds zero user-facing features.** If Stage 3 introduces a feature, Stage 2 was not finished.
- **Failure mode to watch for:** declaring victory. "Added error handling" is not a deliverable. A
  test that spawns a real PTY, navigates into a permission-denied directory, and asserts the app
  stays alive with a visible error message — that is a deliverable.

### Constant across all three

- **Read `docs/STATE.md` first. Update it last.** Every session.
- **Never re-litigate a closed decision.** ADRs exist so the same argument isn't had twice. If you
  disagree with an ADR, write a superseding ADR — don't silently do it your way.
- **When blocked or ambiguous, stop and ask.** A wrong guess propagates through three stages. A
  question costs one message.
- **Never claim a UI outcome you did not render and assert.** See §6.

## 8. Documentation model

Full mechanics live in `AGENTS.md §4`. The one-paragraph version:

`00_PROJECT_INSPIRATION.md` (this file, immutable) establishes the why. `docs/STATE.md` is the live
pointer to where the project actually is. `docs/v1_STAGE_1.md`, `v2_STAGE_2.md`, `v3_STAGE_3.md` are
one per stage; each opens with an **Entry Point** section that says what already exists and links
backward, so later docs never re-explain the project from scratch — you read `v3` plus its entry
point, not all three. Each stage doc is split by a **BUILD LINE**: everything above is a frozen spec
written before work begins, everything below is an append-only implementation log written during.
Decisions that outlive a single stage are promoted to `docs/adr/ADR-000N.md`.

## 9. Definition of "done" for the whole project

`glim` is finished when a developer who has never seen the repo can:

1. `git clone && npm i && npm run dev` and have a working file explorer in under two minutes.
2. Read `docs/v3_STAGE_3.md` §Entry Point and understand the architecture without reading v1 or v2.
3. Run `npm test` and see the real-TTY e2e suite pass.
4. Point it at `/` on a machine with permission-restricted directories and network mounts, mash keys
   for a minute, and not crash it.
5. Read `docs/adr/` and know *why* every non-obvious choice was made.

Anything beyond that is a different project.
